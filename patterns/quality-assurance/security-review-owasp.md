# Pattern: Security Review (OWASP Top 10)

> **TL;DR**: Systematically review all code against OWASP Top 10 vulnerabilities by asking Claude to identify and fix security issues before deployment.

## Overview

The Security Review pattern ensures that all code—whether generated by AI or written by humans—is systematically checked against the OWASP Top 10 security vulnerabilities. This pattern transforms Claude into a security-aware code reviewer that identifies common vulnerabilities like SQL injection, XSS, broken authentication, and insecure configurations.

Security vulnerabilities in production can lead to data breaches, financial loss, and reputational damage. By implementing systematic security reviews early in the development process, you catch vulnerabilities before they reach production, saving time and reducing risk.

This pattern is particularly powerful because Claude has been trained on security best practices and can identify subtle vulnerabilities that developers might miss. Combined with human oversight, it creates a defense-in-depth approach to application security.

---

## Problem It Solves

### The Challenge

Modern applications face constant security threats. The OWASP Top 10 represents the most critical security risks to web applications, and developers frequently introduce these vulnerabilities through:
- Insufficient input validation
- Poor authentication/authorization logic
- Insecure data handling
- Misconfigured security settings
- Lack of security awareness

**Common Symptoms:**
- SQL injection vulnerabilities in database queries
- XSS attacks through unescaped user input
- Authentication bypasses due to flawed logic
- Sensitive data exposure in logs or error messages
- Insecure API endpoints without proper authorization

**Without This Pattern:**
- Security vulnerabilities reach production
- Data breaches expose sensitive customer information
- Attackers exploit authentication flaws
- Injection attacks compromise databases
- Compliance violations lead to legal penalties

### Why Traditional Approaches Fall Short

Traditional security approaches like:
- **Manual code review**: Time-consuming, inconsistent, requires specialized security knowledge
- **Automated scanning tools**: Only catch known patterns, miss logic flaws, produce false positives
- **Penetration testing**: Expensive, done too late in the cycle, reactive not preventive
- **Security training alone**: Developers forget, new vulnerabilities emerge, human error persists

These approaches fail because they're either too late, too shallow, or too dependent on human expertise that may not be consistently available.

## The Solution

### Core Concept

Integrate OWASP Top 10 security checks directly into your development workflow by:
1. Using Claude to review code against each OWASP category
2. Identifying specific vulnerabilities with code examples
3. Getting Claude to propose and implement fixes
4. Validating fixes with security-focused tests
5. Building a security-first development culture

This creates a shift-left security approach where vulnerabilities are caught during development, not after deployment.

### Key Principles

1. **Systematic Coverage**: Check against all OWASP Top 10 categories, not just obvious ones
2. **Context-Aware Analysis**: Consider your specific tech stack and use cases
3. **Immediate Remediation**: Fix issues as soon as they're identified
4. **Defense in Depth**: Layer multiple security controls
5. **Continuous Learning**: Update practices as new vulnerabilities emerge

### How It Works

1. **Code Generation**: Claude generates initial implementation
2. **Security Scan**: Request OWASP Top 10 security review
3. **Vulnerability Identification**: Claude identifies specific security issues
4. **Fix Proposal**: Claude suggests secure alternatives
5. **Implementation**: Claude implements fixes
6. **Validation**: Write tests that verify security controls
7. **Human Review**: Developer validates business logic and threat model

## Implementation

### Basic Implementation

After Claude generates code, always request a security review:

**Prompt Template:**
```markdown
Please review the code you just wrote for OWASP Top 10 vulnerabilities:

1. A01:2021 – Broken Access Control
2. A02:2021 – Cryptographic Failures
3. A03:2021 – Injection
4. A04:2021 – Insecure Design
5. A05:2021 – Security Misconfiguration
6. A06:2021 – Vulnerable and Outdated Components
7. A07:2021 – Identification and Authentication Failures
8. A08:2021 – Software and Data Integrity Failures
9. A09:2021 – Security Logging and Monitoring Failures
10. A10:2021 – Server-Side Request Forgery (SSRF)

For each category:
- Identify any vulnerabilities
- Show the vulnerable code
- Explain the security risk
- Provide a secure fix

Be thorough and critical. Security is critical.
```

**Example Response:**
```
Security Review Results:

A03:2021 – Injection ❌ VULNERABILITY FOUND
Location: api/users.ts:45
Issue: SQL injection vulnerability in user search

Vulnerable code:
  const query = `SELECT * FROM users WHERE name = '${req.body.name}'`;

Risk: Attacker can inject SQL code to access or delete data
Example attack: name = "'; DROP TABLE users; --"

Secure fix:
  const query = 'SELECT * FROM users WHERE name = ?';
  db.query(query, [req.body.name]);
```

Create a custom command for automated security reviews:

**File: `.claude/commands/security-review.md`**
```markdown
# Security Review Command

You are conducting a comprehensive OWASP Top 10 security audit.

## Instructions

1. Analyze all code files in the current changes
2. For each OWASP Top 10 category, systematically check:
   - Is this vulnerability possible in our code?
   - What would exploitation look like?
   - Are current protections sufficient?

3. For each finding:
   - Severity: Critical/High/Medium/Low
   - Location: File and line number
   - Vulnerable Code: Exact code snippet
   - Attack Vector: How it could be exploited
   - Impact: What attacker gains
   - Fix: Secure code implementation
   - Test: How to verify the fix

4. Prioritize findings by severity
5. Implement fixes for Critical and High severity issues
6. Create security tests for all fixes

## OWASP Top 10 Categories

### A01 – Broken Access Control
Check for:
- Missing authorization checks
- Insecure direct object references (IDOR)
- Elevation of privilege
- CORS misconfiguration

### A02 – Cryptographic Failures
Check for:
- Plaintext passwords
- Weak encryption algorithms
- Hardcoded secrets
- Insecure random number generation

### A03 – Injection
Check for:
- SQL injection
- NoSQL injection
- Command injection
- LDAP injection
- XPath injection

### A04 – Insecure Design
Check for:
- Missing rate limiting
- No input validation
- Unlimited resource allocation
- Business logic flaws

### A05 – Security Misconfiguration
Check for:
- Default credentials
- Verbose error messages
- Unnecessary features enabled
- Missing security headers

### A06 – Vulnerable Components
Check for:
- Outdated dependencies
- Known CVEs in packages
- Unmaintained libraries

### A07 – Authentication Failures
Check for:
- Weak password requirements
- No brute force protection
- Insecure session management
- Missing MFA

### A08 – Data Integrity Failures
Check for:
- Unsigned critical data
- Insecure deserialization
- No integrity verification

### A09 – Logging Failures
Check for:
- No logging of security events
- Sensitive data in logs
- No alerting on attacks

### A10 – SSRF
Check for:
- Unvalidated URLs
- Unrestricted outbound requests
- DNS rebinding vulnerabilities

### Configuration

Create a pre-commit hook for automated security checks:

**File: `.git/hooks/pre-commit`**
```bash
#!/bin/bash

echo "Running security review..."

# Check for common secrets
if git diff --cached | grep -E "(password|api_key|secret|token)\s*=\s*['\"][^'\"]+['\"]"; then
    echo "❌ Potential hardcoded secret detected!"
    echo "Please use environment variables for sensitive data."
    exit 1
fi

# Check for SQL concatenation (potential injection)
if git diff --cached | grep -E "SELECT.*\+.*\$|INSERT.*\+.*\$"; then
    echo "⚠️  Potential SQL injection pattern detected"
    echo "Please use parameterized queries."
    exit 1
fi

echo "✅ Basic security checks passed"
```

Make it executable:
```bash
chmod +x .git/hooks/pre-commit
```

## Complete Code Example

### Scenario

You're building a user authentication API with login, password reset, and profile viewing functionality.

**Requirements:**
- User login with email/password
- Password reset functionality
- User profile endpoint
- Secure against OWASP Top 10

### Implementation

**File: `api/auth.ts`**
```typescript
import bcrypt from 'bcrypt';
import jwt from 'jsonwebtoken';
import { rateLimit } from 'express-rate-limit';
import validator from 'validator';
import { db } from './database';

// A04 – Insecure Design: Rate limiting to prevent brute force
const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 5, // 5 attempts
  message: 'Too many login attempts, please try again later'
});

export async function login(req, res) {
  try {
    const { email, password } = req.body;

    // A03 – Injection: Input validation
    if (!validator.isEmail(email)) {
      return res.status(400).json({ error: 'Invalid email format' });
    }

    // A03 – Injection: Parameterized query (prevents SQL injection)
    const user = await db.query(
      'SELECT id, email, password_hash FROM users WHERE email = ?',
      [email]
    );

    if (!user) {
      // A09 – Logging: Log failed login attempts
      logger.warn('Failed login attempt', { email, ip: req.ip });

      // A07 – Authentication: Generic error message (prevents user enumeration)
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    // A02 – Cryptographic Failures: Use bcrypt for password comparison
    const isValid = await bcrypt.compare(password, user.password_hash);

    if (!isValid) {
      logger.warn('Failed login - invalid password', { email, ip: req.ip });
      return res.status(401).json({ error: 'Invalid credentials' });
    }

    // A02 – Cryptographic Failures: Secure JWT token
    const token = jwt.sign(
      { userId: user.id, email: user.email },
      process.env.JWT_SECRET, // Secret from env, not hardcoded
      { expiresIn: '1h', algorithm: 'HS256' }
    );

    // A05 – Security Misconfiguration: Secure cookie settings
    res.cookie('token', token, {
      httpOnly: true,  // Prevents XSS access to cookie
      secure: true,    // HTTPS only
      sameSite: 'strict', // CSRF protection
      maxAge: 3600000  // 1 hour
    });

    // A09 – Logging: Log successful login
    logger.info('Successful login', { userId: user.id, ip: req.ip });

    return res.json({ success: true });

  } catch (error) {
    // A09 – Logging: Log errors without exposing sensitive data
    logger.error('Login error', { error: error.message });

    // A05 – Security Misconfiguration: Generic error message (no stack traces)
    return res.status(500).json({ error: 'An error occurred' });
  }
}

// A01 – Broken Access Control: Authorization middleware
export function requireAuth(req, res, next) {
  const token = req.cookies.token;

  if (!token) {
    return res.status(401).json({ error: 'Not authenticated' });
  }

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.userId = decoded.userId;
    next();
  } catch (error) {
    logger.warn('Invalid token', { ip: req.ip });
    return res.status(401).json({ error: 'Invalid token' });
  }
}

// A01 – Broken Access Control: Prevent IDOR
export async function getUserProfile(req, res) {
  const requestedUserId = req.params.userId;
  const authenticatedUserId = req.userId;

  // Users can only view their own profile
  if (requestedUserId !== authenticatedUserId) {
    logger.warn('Unauthorized profile access attempt', {
      requestedUserId,
      authenticatedUserId,
      ip: req.ip
    });
    return res.status(403).json({ error: 'Access denied' });
  }

  // A03 – Injection: Parameterized query
  const user = await db.query(
    'SELECT id, email, name, created_at FROM users WHERE id = ?',
    [authenticatedUserId]
  );

  return res.json(user);
}
```

**File: `middleware/security-headers.ts`**
```typescript
// A05 – Security Misconfiguration: Security headers
export function securityHeaders(req, res, next) {
  // Prevent clickjacking
  res.setHeader('X-Frame-Options', 'DENY');

  // Prevent MIME sniffing
  res.setHeader('X-Content-Type-Options', 'nosniff');

  // Enable XSS filter
  res.setHeader('X-XSS-Protection', '1; mode=block');

  // Content Security Policy
  res.setHeader('Content-Security-Policy', "default-src 'self'");

  // HSTS (force HTTPS)
  res.setHeader('Strict-Transport-Security', 'max-age=31536000; includeSubDomains');

  next();
}
```

```bash

## When to Use

### Ideal Use Cases

✅ **Use this pattern when:**
- Building authentication/authorization systems
- Handling user input (forms, APIs, search)
- Processing sensitive data (PII, financial, health)
- Developing public-facing applications
- Working with databases or external APIs
- Implementing file uploads or downloads
- Creating admin panels or privileged functionality

### Indicators You Need This Pattern

- You're storing user data
- Your app handles money or sensitive information
- You have user authentication
- You accept user input
- You're building APIs
- Compliance requirements (GDPR, HIPAA, PCI-DSS)
- You're deploying to production

### Project Types

**Best For:**
- Web applications
- REST/GraphQL APIs
- Mobile app backends
- SaaS platforms
- E-commerce sites
- Healthcare/financial applications

**Also Works For:**
- Internal tools (still need security!)
- Prototype → production transitions
- Legacy code modernization

## When NOT to Use

### Avoid This Pattern When

❌ **Don't skip security reviews if:**
- Your app handles real user data (always review!)
- You're deploying to production (always review!)
- "It's just a prototype" (prototypes become production!)

⚠️ **Lower priority for:**
- Throwaway scripts (never deployed)
- Isolated research code (no network access)
- Completely internal, non-networked tools

### Simpler Alternatives

For extremely simple cases:
- **Basic Input Validation**: If you only need to validate specific inputs
- **Framework Security Features**: Use built-in security (e.g., Django ORM auto-escaping)

### Warning Signs

⚠️ **You're doing it wrong if:**
- Security review takes longer than implementation (simplify your code)
- Every review finds 10+ critical issues (learn security basics first)
- You skip reviews "because we're behind schedule" (security debt compounds)

## Common Pitfalls & Solutions

### Pitfall 1: Checkbox Mentality

**Problem**: Treating security review as a checklist without understanding vulnerabilities

**Solution**: For each vulnerability type, understand:
- How the attack works
- What damage it causes
- How the fix prevents it

```typescript
// ❌ Wrong: Just using parameterized queries without understanding why
db.query('SELECT * FROM users WHERE id = ?', [id]);

// ✅ Correct: Understanding SQL injection and defense
// This prevents SQL injection because the query structure is
// separated from user data. Even if 'id' contains SQL code,
// it's treated as a string literal, not executable SQL.
db.query('SELECT * FROM users WHERE id = ?', [id]);
```

### Pitfall 2: Relying Solely on AI

**Problem**: Assuming Claude catches all vulnerabilities without human oversight

**Solution**:
- Claude identifies common patterns
- Humans validate business logic and threat model
- Use both AI analysis and human expertise

### Pitfall 3: Generic Fixes Without Context

**Problem**: Applying security patterns that don't fit your use case

**Solution**: Consider your specific threat model:

```typescript
// ❌ Wrong: Overly restrictive for internal admin tool
app.use(rateLimit({ windowMs: 60000, max: 1 })); // 1 request/minute

// ✅ Correct: Appropriate limits for use case
// Public API: strict limits
app.use('/api/public', rateLimit({ windowMs: 60000, max: 100 }));
// Admin API: more permissive (authenticated users only)
app.use('/api/admin', requireAuth, rateLimit({ windowMs: 60000, max: 1000 }));
```

### Pitfall 4: Security Theater

**Problem**: Implementing security that looks good but doesn't actually protect

**Solution**: Test your security controls:

```typescript
// ❌ Security theater: Client-side validation only
<input type="email" required />  // Attacker bypasses this in 2 seconds

// ✅ Real security: Server-side validation
if (!validator.isEmail(email)) {
  return res.status(400).json({ error: 'Invalid email' });
}
// Client-side validation is UX, not security
```

## Best Practices

### Do's ✅

- **Always review before merging**: Make security review mandatory
- **Fix immediately**: Don't accumulate security debt
- **Test your fixes**: Write tests that prove vulnerability is fixed
- **Layer defenses**: Use multiple security controls (defense in depth)
- **Keep learning**: OWASP Top 10 updates periodically
- **Document assumptions**: Note threat model and security boundaries

### Don'ts ❌

- **Don't skip reviews when "behind schedule"**: Security debt compounds
- **Don't assume frameworks handle everything**: Validate this assumption
- **Don't hardcode secrets**: Use environment variables and secret management
- **Don't trust user input**: Ever. Validate and sanitize everything
- **Don't expose sensitive errors**: Generic messages to users, detailed logs internally

### Pro Tips 💡

- **Tip 1**: Ask Claude "What's the worst-case scenario if an attacker controls this input?" for each user-controlled variable
- **Tip 2**: Review authentication/authorization logic with extra scrutiny—these bugs are often subtle
- **Tip 3**: Set up automated dependency scanning (e.g., `npm audit`, Dependabot) for A06
- **Tip 4**: Use security linters (e.g., ESLint security plugins) to catch issues during development
- **Tip 5**: Create a threat model document for your application to focus reviews on high-risk areas

## FAQ

### Q: Should I do this for every single code change?

A: Focus on security-sensitive changes:
- **Always**: Authentication, authorization, data handling, user input
- **Often**: API endpoints, database queries, file operations
- **Sometimes**: UI components (check for XSS), utility functions
- **Rarely**: Pure business logic with no external inputs

### Q: What if Claude says "no vulnerabilities found" but I'm not confident?

A: Be specific about your concerns:
```
I'm concerned about SQL injection in the search functionality.
Walk me through how the query is constructed and why it's safe.
Show me what happens if an attacker provides: ' OR '1'='1
```

### Q: How do I balance security with development speed?

A: Security reviews are faster than security incidents:
- Use custom commands to automate reviews
- Build security knowledge over time (gets faster)
- Fix patterns, not individual instances
- Security debt is expensive—pay it early

### Q: What about vulnerabilities not in OWASP Top 10?

A: OWASP Top 10 covers the most common/critical risks. For comprehensive security:
- Add specific checks for your domain (e.g., business logic flaws)
- Keep dependencies updated
- Conduct periodic penetration testing
- Stay informed on new vulnerability types
